## 一、缓存测量法

### 数据从哪来

pi 的会话文件 `~/.pi/agent/sessions/<cwd编码>/<时间戳>_<sessionId>.jsonl`，
每行一条 JSON，`type: "message"` 的行里 `message.usage` 带用量：

```json
{
  "input": 213,        // 未命中缓存的 token（按 miss 价计费）
  "cacheRead": 146688, // 命中缓存的 token（按 hit 价计费）
  "cacheWrite": 0,
  "output": 224
}
```

**`cacheRead` 就是命中量。** 想知道缓存有没有工作，看这个数。

### 一条命令看全貌

```bash
F=$(ls -t ~/.pi/agent/sessions/--C--Users-Cros--/*.jsonl | head -1)
python - "$F" <<'PY'
import json, sys
i = 0
for line in open(sys.argv[1], encoding="utf-8"):
    try: e = json.loads(line)
    except Exception: continue
    if e.get("type") != "message": continue
    m = e.get("message") or {}
    if m.get("role") == "system" and m.get("sections"):
        print("  [system 补丁] %s" % list(m["sections"].keys()))
    u = m.get("usage")
    if u:
        i += 1
        print("%3d | input=%6s | cacheRead=%8s" % (i, u.get("input"), u.get("cacheRead")))
PY
```

### 怎么判断"缓存坏了"

```
正常：input 稳定在几百，cacheRead 逐轮增长
坏了：cacheRead 卡在某个固定值，input 逐轮增长
```

**卡住的那个数字，就是失效点的位置。** 例如 cacheRead 卡死在 2048，
说明前 2048 token 还命中，之后全 miss——第 2048 个 token 处有内容变了。

## 二、A/B 对照实验法

### 结构

```
1. 加一个 env 开关（不改变默认行为）
     if (process.env.MEM_TEST_FLIP === "1") { ...改动... }
2. 跑对照组：N 轮，不带开关
3. 跑实验组：N 轮，带开关
4. 对比 cacheRead / input / system 条目数
5. 还原代码，删掉测试会话
```

### 关键细节

- **每组至少 10 轮**。前 1–4 轮可能是冷缓存，第 5 轮之后才稳定
- **两组的对话内容要一致**（同样的短句），否则变量不唯一
- **跑完删掉测试会话**，否则污染后续统计
- **改完代码必须同步到安装目录**，否则 `pi` 加载的还是旧版

### 这次实验的教训

第一次跑 5 轮对照，cacheRead 一直是 0，看起来像"缓存完全不工作"。
跑到 10 轮才看到从第 2 轮开始稳定命中。

**5 轮不够。样本太少时，结论可能是启动开销而不是机制。**

## 三、成本折算法

### 把所有东西折算成同一个单位

不同 token 单价不同，直接相加没意义。统一折算成 **miss 等效 token**：

```
等效 = miss_token + cacheRead × (hit_price / miss_price)
```

deepseek-v4.1-flash：hit $0.003/M，miss $0.15/M → 系数 **0.02**（1/50）。

### 算一次会话

```
每轮成本 = 每轮新增 miss + 上下文 × 0.02
总成本   = 每轮成本 × 轮数
```

### 算增幅

```
增幅 = (有插件成本 / 无插件成本) - 1
```

### 注意：增幅和绝对值不是一回事

```
20K 上下文 / 每轮 500：增幅 +15.5%，但绝对值只有 $0.0004
100K 上下文 / 每轮 2000：增幅 +3.5%，绝对值 $0.0021
```

**上下文越大，增幅越小**——因为缓存的 token 占大头，而它便宜 50 倍。

**别只看百分比。** 小会话增幅吓人但金额可以忽略。

### 一次性成本要单独算

```
重锚一次 = 上下文大小 × 1（全量 miss）
100K 上下文重锚一次 = 100K 等效 token = 25 轮正常开销
```

**周期性的小开销，往往比偶发的大开销便宜。**
优化前先算清楚哪个占大头。

## 四、检索评测法

### 两种题，夹逼真实水平

| 出题方式 | 特点 | 结果 |
|---|---|---|
| 自己手写 | 措辞贴近记忆原文 | 偏乐观（Hit@3 92%） |
| 让子代理看答案出题 | 更抽象 | 偏严格（Hit@3 70%） |

**真实水平在两者之间。** 只报一个数是自欺。

### 不能用 turn 级 provenance 当真值

试过用"原始用户提问 + 蒸馏记忆的来源 turn"做真值，**命中率 0%**。

原因不是检索差，是真值错：助手一轮回答覆盖多个话题，
按 turn 对齐必然错位。

**可行方式只剩两种**：人工出题，或 LLM 反向生成。

### 小样本的陷阱

13 道题，一道题就是 8 个百分点。**统计上不显著**，
所以每次调参都要跑同一套题，看趋势不看单点。

## 五、写补丁脚本的纪律

### bash heredoc 会吃掉转义

```bash
python - <<'PY'
s = s.replace('a', 'b\\n')   # 实际写进去的是真的换行，不是 \n
PY
```

**修法**：用 `chr(92)` 拼反斜杠，或者用 write 工具写脚本文件再执行。

```python
BS = chr(92)
fixed = 'text += "' + BS + 'n";'
```

### 每次替换都要 assert 锚点

```python
assert old in s, "锚点没找到"
s = s.replace(old, new)
```

否则替换静默失败，后面所有基于它的改动全错。

### 改完立刻做语法检查

```python
python -c "import ast,io;ast.parse(io.open('mem.py',encoding='utf-8').read())"
```

TypeScript 用 esbuild：

```bash
node -e "
const esbuild=require('<path>/esbuild');
esbuild.build({entryPoints:['x.ts'],bundle:false,write:false,loader:{'.ts':'ts'}})
 .then(()=>console.log('OK')).catch(e=>console.log(e.errors));
```

## 六、Windows 环境的三条铁律

1. **管道默认 GBK** —— 输出非 ASCII 会 `UnicodeEncodeError`，
   子进程静默失败。必须 `PYTHONIOENCODING=utf-8` + `sys.stdout.reconfigure`
2. **`detached: true` + `stdio: "ignore"` + `unref()`** 三件套，
   子进程才能在父进程退出后继续跑
3. **路径反斜杠** —— 写进 JSON 或正则时要转义，用 `/` 更省事

## 七、什么时候该停下

三条止损信号：

1. **同一个小改动改了三遍还不对** → 停下来看设计，不是继续改
2. **评测数字在噪声范围内摆动** → 样本不够，先加样本
3. **做出来的东西自己不会用** → 想想是不是在解决不存在的问题

第 3 条最贵。`pi-observational-memory` 有 752 stars，
我们花两周做功能更少的东西之前，先问一句"真的需要吗"。

# 段索引 · 方案对比与决策

> 2026-11-10 · 讨论记录。等这条路线定了，再把结论并回 `AGENT_HANDOFF.md`
> 起因：想改成"每轮收口"，需要先算清 token 代价，并把「收口 / 摘要 / 注入」三件事解耦。

---

## 0. 一句话结论

**收口不花钱，摘要才花钱。** 收口每轮做（本地写库，0 token）；摘要按事件做（一次 LLM 调用，贵）；注入保持稀疏（只在两个时刻）。

L2 的输出**本来就不进正文**，只落盘。所以"摘要存本地硬盘"不能省钱——省的是它带来的副作用：可以延后、可以批量、可以重试。

---

## 1. 三个动作，必须分开看

| 动作 | 做什么 | 在哪跑 | token 成本 |
|---|---|---|---|
| **收口 close** | 把当前段的指针（first_id/last_id/轮次/原文路径）写成一条 `mem_segments` | 本地 SQLite | **0** |
| **摘要 L2** | 一次 LLM 调用：段原文 → title / digest / statements[] / 向量 | 后台进程 | **贵**（见 §3） |
| **注入 inject** | 把一行或一块文本塞进上下文（system 或 tail） | 宿主 | 每轮或每次计费 |

现在代码把三者绑在一起：段闭合 → 同轮注入 `[mem:seg]` 行 → 会话结束 → L2。
这次要拆的就是这个绑定。

## 2. 实测基线（本会话，真实 usage）

| 指标 | 值 |
|---|---|
| 用户轮 / 模型调用 | 7 轮 / **115 次**（每用户轮 16.4 次调用，工具循环导致） |
| 每次调用 miss | 1,530（累计 174,439） |
| 每次调用 cacheRead | 76,332（占输入侧 **98.0%**） |
| 每次调用 output | 581 |
| 每用户轮原文 | 平均 **9.7K token**（中位 5K，最大 24.8K） |
| 每用户轮总输入 | ≈ 1.28M token，其中 miss **25K** |

**杠杆点**：cacheRead 占输入量 98%，单价约为 miss 的 1/10。
所以"看起来只多 0.7% 的 token"，在**花费**上可能是 6%。算账必须按 miss 计价折算。

## 3. L2 的真实成本

```
每次 L2 输入 ≈ 700（SEGMENT_PROMPT）+ min(段原文, 24000 字符 ≈ 8K token)
每次 L2 输出 ≈ 300（JSON：title + digest + 0~4 条 statements）
全部按 miss 计价：L2 是独立短上下文，吃不到任何缓存
```

**注意一个现有缺陷**：`_seg_source_text` 取的是 `text[-max_chars:]`（只保留**末尾** 24000 字符）。
15 轮一段时，一个段可能 20K+ token，L2 实际只看到最后两三轮 —— "去指代"能力因此打折。
每轮一段反而没有这个问题（单轮 9.7K < 8K 上限附近）。

### 3.1 实测量（2026-11-10，本会话 9 轮 / 160K 上下文）

| 量 | 实测值 |
|---|---|
| `SEGMENT_PROMPT` | **480 token** |
| 4 个段的原文（真实 tokenizer） | 12,154 / 41 / 3,819 / 3,283 |
| 唯一真跑过的一次 L2（seg-3b420f） | 输入 12,634 + 输出 1,961 = **14.6K** |
| 4 段都跑（按已跑那段的输出/输入比 0.16 估） | 输入 21.2K + 输出 5.9K = **约 27K** |
| 若改成每轮摘要（9 轮） | 约 **150K**（≈ 上下文本身） |

换算：L2 输入 100% miss，主对话 98% 是 cacheRead。
所以 27K 的 L2 ≈ 相当于 270K 的 cacheRead —— **同样的 token 数，钱的差 10 倍**。

另外实测发现两个偏差，都会让估算失真：

1. `n_tokens()` 被 tokenizer 默认截断卡在 **256**（21023 字符 → 报告 256，真实 12,154）。凡是用它做预算的地方全部低估
2. `CHARS_PER_TOKEN` 把中文按 3 字符/token 算，真实约 **1.73**（12154/21023）→ 段容量和 turn_tokens 都低估约 1.7 倍
3. 单轮段的 `first_id == last_id`，按区间切片只取到 **1 条消息**（41 token）→ 单轮段几乎无法摘要，这是"每轮收口"必须先解决的问题

### 频率对比（每天按 50 个用户轮算）

| 摘要策略 | 调用次数 | L2 总输入 | 相对现状 |
|---|---|---|---|
| 现状：15 轮一段 | 4 | **32K** | 1× |
| 每轮一段 | 50 | **435K** | **13×** |
| 每轮一段 + 批量（5 段一调用） | 10 | 43K + 固定开销 6K | 1.5× |

## 4. 方案矩阵

### 4.1 收口触发方式

| 代号 | 方式 | token | 断电窗口 | 段粒度 | 备注 |
|---|---|---|---|---|---|
| C0 | 硬上限 15 轮 / 12000 token（**现状**） | 0 | 几分钟~整天 | 粗 | 段大、L2 输入被截断 |
| C1 | **每轮收口** | **0** | **0~1 轮** | 细（1 轮） | 行数从每天 4 变成 50 |
| C2 | 每轮记"轮记录"，每 N 轮合并成段 | 0 | 0~N 轮 | 中 | 需要多一张表 |
| C3 | 只在会话结束 / 切走 / drain | 0 | 分钟级 | 粗 | 断电就丢 |

### 4.2 摘要时机

| 代号 | 方式 | 相对现状花费 | 质量 |
|---|---|---|---|
| L0 | 不摘要（只有 L1 截断标题） | 0 | 差：无 statements、无 decision 提升 |
| L1 | 每段收口时一次（**现状**） | 1× | 好（段内有上下文） |
| L2a | 每轮一次（收口即摘要） | **+6%** | 差：段内只有 1 轮，去指代失效 |
| L2b | 每轮收口 + 批量摘要（N 段一调用） | +1% 内 | 中（仍缺跨轮上下文） |
| L3 | 队列延后（关闭后 / 下次启动 / 失败重试） | 1× | 好，且不怕断电 |
| **L4** | **主模型 inline 输出**（tool call 写回） | **0.3×** | 最好（上下文完整，去指代天然成立） |

### 4.3 注入方式（这是"解耦"的核心）

| 代号 | 注入什么 | 时机 | 每次 token | 每轮 token | 缓存影响 |
|---|---|---|---|---|---|
| I0 | 什么都不注入 | — | 0 | 0 | 无 |
| I1 | `[mem:domains]` 相关历史会话 | 新会话第一轮 | ~60 | 0 | 无（进 tail） |
| I2 | `[mem:seg-index]` 最近 N 段 | 压缩后第一轮 | ~380（5 段） | 0 | **无**（压缩已作废前缀，天然 miss 点） |
| I3 | `[mem:seg]` 刚归档的那一段 | 段闭合当轮（**现状**） | ~45 | 0（偶发） | 无 |
| I4 | 最近 N 段摘要 | 每轮 | — | +380 | 无（tail 本来就每轮变） |

## 5. 「收口 / 注入」解耦方式对比（重点）

| 方式 | 收口时机 | 注入时机 | 每轮额外 token | 断电风险 | 模型可发现性 | 结论 |
|---|---|---|---|---|---|---|
| **D0 现状：事件耦合** | 段闭合 | 同一轮 `[mem:seg]` | 0（偶发 45） | 高（状态靠关闭收口） | 中 | 保留，但不作为唯一通道 |
| **D1 完全解耦（推荐）** | **每轮**收口，本地 | 只在 I1 + I2 两个时刻 | **0** | **0~1 轮** | 中（压缩后能看到） | ✅ 主线 |
| D2 半解耦 | 每轮收口 | 收口只写 customEntry（不进上下文），注入仍靠 I1+I2 | 0 | 0~1 轮 | 低 | 和 D1 等价，只是少了 I3 |
| D3 延迟一轮注入 | 每轮收口 | 下一轮注入上一段指针 | 0（错峰 45） | 0~1 轮 | 中 | 适合"怕打断当前话题"，代价是慢一拍 |
| D4 纯拉取 | 每轮收口 | 完全不注入，靠 `mem_search` | 0 | 0~1 轮 | **低**（模型不知道有段） | 只作兜底 |

**D1 的完整时序**：

```
用户消息 ──► retrieve ──► 本轮回复
                │
                └─ track_segment：更新状态 → 每轮收口（本地写一条 1 轮段）
                                    └─ 入队 enrich（不阻塞）

新会话第一轮  ──► tail 注入 [mem:domains]（I1）
压缩成功后第一轮 ──► tail 注入 [mem:seg-index]（I2）
drain（启动时/空闲时）──► 批量 L2：把排队的段一次性摘要完
```

**为什么 D1 不掉缓存**：注入仍只在两个"前缀本来就要重写"的时刻发生——新会话（无前缀可复用）和压缩后（前缀已被作废）。中间的每一轮既不碰 system，也不重复注入。

## 6. 当下路线（建议拍板）

```
① 收口：每轮（C1），纯本地，0 token
② 摘要：事件驱动 + 队列（L3），批量、可重试、不怕断电
③ 注入：只在 I1 + I2（D1），其余不注入
④ drain：启动时扫 stale 状态行（session 文件 mtime < now-300s）补收口
```

代价与验证点：

| 项 | 数值 |
|---|---|
| token 增量 | **0**（收口本地、注入稀疏） |
| `mem_segments` 增长 | 每天约 50 行（SQLite 几 KB） |
| 检索影响 | 2000 段时域激活仍 ~110ms（实测过 1997 条 109ms） |
| 断电丢失 | 最多最后 1 轮的收入段（内容仍在会话 JSONL） |

## 7. 实现要点（决定路线后再动手）

1. **幂等**：`mem_segments(session_id, seq)` 加唯一索引；收口在事务内 `DELETE state WHERE session_id=?` 返回 1 才继续
2. **drain 判定**：`state.session_id != 当前` 且 `会话 JSONL mtime < now-300s`；拿不到 mtime 退回 `opened_at`
3. **enrich 队列**：复用 `harvest_jobs` 模式（pending/running/heartbeat/failed），最多 3 次重试
4. **修 promote 顺序**：现在先置 `enriched=1` 再 promote，promote 异常被吞 → decision/rejected 永久丢失。改成先 promote 成功再置位，或把 `promoted` 结果写进段
5. **尺寸统一**：提示词要求 title ≤20 字 / digest ≤120 字，代码截断是 40 / 200。建议统一到提示词侧
6. **注入块尺寸**（I2）：5 段 × (title 20 + digest 截 40) ≈ **380 token**，一次性

## 9. 附：本轮讨论中被否掉的

- **"L2 输出存本地硬盘以省 token"** —— ❌ 前提不成立：L2 输出本来就没进正文，只落盘（`mem_segments` + `mem_items`）。存哪不影响生成成本。
- **"每轮收口 + 每轮摘要"** —— ❌ token 13 倍，且破坏"去指代"质量（每段只有 1 轮上下文，用户说"可以"时无法还原）。
- **"完全靠模型主动 mem_search，不注入"** —— ❌ 可发现性太低，模型不知道历史段存在就不会查。

## 10. 澄清：两条成本线互不影响

这是最容易搞混的地方，单独记一笔。

### 10.1 两个完全独立的请求

| | 主对话请求 | L2 请求 |
|---|---|---|
| 什么时候发 | 每轮，用户等着 | 后台，没人等 |
| 输入是什么 | system prompt + 历史消息（含 tail）+ 用户消息 | `SEGMENT_PROMPT` + 磁盘上的段原文 |
| 数据从哪读 | 模型上下文 | **直接读会话 JSONL 文件**（`_seg_source_text`） |
| 缓存状态 | 占了输入侧 98%，是 cacheRead | **永远 100% miss**，从来不是缓存价 |
| 谁影响它 | 只有 system section 变化会把它打穿 | 与主对话缓存毫无关系 |

**所以：不是"有了摘要/指针，L2 就从缓存价变 miss"。L2 从来就是 miss，因为它是一个短命请求，没有前缀可复用。**

摘要和指针影响的是**主对话**的缓存，因为它们是拼进主对话上下文的。

### 10.2 摘要/指针放哪里，价差 10 倍

| 位置 | 每轮成本 | 机制 |
|---|---|---|
| **数据表**（只落盘，不注入） | **0** | 只有被检索时才产生 token |
| **system section** | cacheRead 价（约 1/10） | 前提：字节逐字节不变 |
| **tail**（文字段末尾） | **全价 miss** | 每轮是新消息，永远不进缓存 |

推论：

- **摘要正文**（120~300 token）只能进数据表。放进 system，一旦新增段就改变前缀 → 从该位置起全部作废（实测过：input 从 340 涨到 3250）
- **指针**（45~380 token）放 tail，且必须稀疏；每轮都放 = 每轮全价
- 所以现在的分工是对的：**全量摘要进表，末尾只放一行指针**

### 10.3 真正可调的就是"多久放一次"

| 放什么 | 时机 | 一次性成本 |
|---|---|---|
| `[mem:domains]` | 新会话第一轮 | ~60 |
| `[mem:seg]` 指针行 | 段闭合当轮 | ~45 |
| `[mem:seg-index]` 指针块 | 压缩后第一轮 | ~380 |
| 摘要正文（digest 全文） | 压缩后第一轮（可选替代指针） | ~600（5 段 × 120） |

最后一行的选项值得试：压缩后直接给**摘要全文**而不是指针，模型不用再 `segment get` 就能接上历史。一次性 600 token，之后全靠 cacheRead。

## 11. 主模型 inline 做 L2 vs 后台 L2

### 11.1 成本对比（按 §3.1 实测量）

| | 后台 L2 | 主模型 inline |
|---|---|---|
| 输入 | 480 + 段原文（实测 12,154）= **12,634 miss** | **0**（已在上下文，cacheRead） |
| 输出 | 1,961 | 1,961（走 tool call 参数，不进正文） |
| 后续历史 | 0 | +2K，之后每轮 ~200 cacheRead |
| 额外请求 | 1 次（占配额） | 0 |
| miss 等价（out 按 3× 计） | **18,517** | **5,883** |

→ **inline 便宜约 3 倍**，且不占额外配额。每轮摘要的话差距更大（150K vs 30K）。

### 11.2 为什么仍然要保留后台 L2

| 约束 | 说明 |
|---|---|
| 不可重放 | inline 摘要依赖当时对话状态，同样的段原文重跑不出同样结果；后台是固定提示词，可重放可审计 |
| 无兜底 | 模型忘了调工具 / 输出非法 JSON → 这条记录直接丢；后台有队列可重试 |
| 注意力干扰 | 收口发生在解题中途，要模型额外产 2K 结构化输出，两个任务互相干扰 |
| 自我强化 | 模型不断看到自己的总结，容易把误解写进长期记忆并反复引用 |
| 断电 | 进程被杀时 inline 没机会跑；后台可以下次启动补 |

### 11.3 建议：inline 为主，后台兜底

```
常态：段闭合那一轮，tail 加一行提示 +
      注册工具 mem_seg_close(title, digest, statements[])
      模型调 → 写入 mem_segments（enriched=1）

兜底：drain 时扫 enriched=0 的段 → 后台 L2（带重试上限）

校验：inline 写入后跑一次轻量校验（title ≤20 字、至少 1 条陈述、无代词残留）
      不过 → 打回后台重做
```

代价：工具 schema 进 system prompt（约 150 token，一次性，之后 cacheRead），
提示行只在段闭合当轮出现（~30 token）。

### 11.4 实测对比（2026-11-10，seg-20261110-2e1f62，turn 5–7，原文 6,606 字符）

| 指标 | 后台 L2 | inline（主模型） |
|---|---|---|
| 陈述数 | **36** | **12** |
| 输出 token | 3,559 | 1,246 |
| 输入 token | 4,299（全 miss） | 0 |
| miss 等价（输出×3） | **14,976** | **3,738** |
| title / digest | 14 / 86 | 13 / 53 |
| 事实覆盖 | pi-web 内部常量（600000、SIGTERM、session_compact、appendCustomMessageEntry）、scanSession 规则 | 成本实测数（16.4、76,332、98.0%、13 倍、435K、380 token） |
| 污染 | 保留已被后续推翻的“5 行约 200 token”；3 条“尚未解决”其实已在下一轮回答 | 无 |

**结论：inline 成本 1/4、输出 1/3、噪声更少。后台 L2 抓细节更强，但会“凑数”并把已答问题记成 question。**

### 11.5 但这次 A/B 撞出两个真 bug

1. **`last_id` 边界丢最后一条助手回答**
   `_seg_close` 传入的 `last_id` 是**触发收口的那条用户消息**，所以该用户消息之后的助手回答永远不在原文里。
   本次实测：段原文 6,606 字符里只有 4 条 assistant 且都是开头过渡句，我的设计正文和成本数字全miss。
   → 背景 L2 只能看到“用户的提问”而看不到“我的回答”，所以它把已答事项记成了 `question`。
   → 若改成每轮收口，每段将**只含用户消息**，助手内容全部丢失。

2. **`first_id` 为空时回退到整个会话文件**
   seg-3b420f（turn 1–3）因为 `first_id=''`，实际取了整个会话的**最后 24,000 字符**，
   输出里出现了 turn 8–9 才发生的事（“7788 端口没有 daemon”）。即：那段摘要根本不属于它自己的段。

**所以：inline 不受这两个 bug 影响（材料在上下文里，不靠指针切片），后台 L2 必须先修切片才可信。**

### 11.5.1 修完切片后重跑（同一段，seg-2e1f62）

修复内容：`_seg_source_text` 改为**按 turn 序号切片**（start = 第 turn_start 条用户消息，end = 第 turn_end+1 条用户消息**之前**），id 区间只作回退且同样向后延伸；`segment get --part` 改为复用同一个函数。

| 指标 | 后台 v1（切片坏） | 后台 v2（修好） | inline |
|---|---|---|---|
| 陈述数 | 36 | **22** | 12 |
| 输出 token | 3,559 | 3,117 | 1,246 |
| 输入 token | 4,299 | 5,490 | 0 |
| miss 等价 | 14,976 | 14,841 | **3,738** |
| 成本数字覆盖 | ✗ | **✓** | ✓ |
| 虚假 question | 3 | 0（2 条真未决） | 0 |

**结论反转了一半**：修完切片后，后台 L2 的质量反超 inline（覆盖 drain 判定、L2 失败因、promote bug、三层尺寸、提示词要求），代价只是 4 倍 token。

但绝对金额很小：每段约 14.8K miss，按 $0.28/M 算约 **$0.004/段**；一天 4 段约 **$0.016**，一个月 $0.5。
与 inline 的差额不到 $0.5/月。

→ **不值得为了这点钱引入 inline 的工具注入、历史污染和不可重放。**
→ 建议：后台 L2 做主路（简单、可重放、可重试）；inline 留作重大决策段的补充选项。

### 11.6 最终建议

```
1. 先修切片（last_id 要指向该段最后一轮的助手回答；first_id 为空时按 turn 序号兜底）
2. inline 为主：段闭合当轮注入一行提示（~30 token）+ 工具 mem_seg_close
3. 输出限幅：陈述 ≤ 8 条、禁止无意义 question、过滤“已完成：XXX”类任务日志
4. 后台兜底：drain 时处理 enriched=0 的段（带 3 次重试上限）
```

## 12. 向量契合度实测（2026-11-10）

### 12.1 决定性事实：嵌入被截断在 256 token

`mem.py:160` 显式 `_TOK.enable_truncation(max_length=256)`。
所以**所有向量只看前 256 token**（记忆条目、段、陈述都一样）。

实测 seg-2e1f62：

| | 全量 token | 实际进入向量 | 窗口里能放下的陈述 |
|---|---|---|---|
| v2（22 条陈述） | 1,947 | **256** | 头部 111 + 陈述#1（132）→ **只剩 1 条** |
| inline（12 条陈述） | ~1,200 | 256 | 头部 40 + 陈述#1~3 → **3 条** |

**推论：陈述写多少条对段检索几乎无影响，因为超出的部分根本没进向量。**
"过多事实稀释向量"不成立；真实情况是"过多事实根本进不了向量"。

### 12.2 四个候选的分离度（e5-small，生产截断）

| 候选 | 嵌入 token | pos 均值 | neg 均值 | 分离度 |
|---|---|---|---|---|
| D pi-mem 风格固定叙事 | 104 | 0.885 | 0.854 | **0.031** |
| B inline（12 陈述） | 256 | 0.886 | 0.861 | 0.025 |
| C 只 title+digest | 111 | 0.879 | 0.858 | 0.021 |
| A v2（22 陈述） | 256 | 0.883 | 0.865 | 0.019 |
| E 只有陈述（假设） | 256 | 0.876 | 0.860 | 0.016 |

全部落在 0.01–0.03 的已知噪声带（handoff §6 坑 6：50 段时信号/噪声只差 0.01–0.03）。
**方向**支持"短而结构化 > 堆陈述"，但**幅度不足以作为决策依据**。

### 12.3 真正能控的三件事

1. **title 短、digest 精** —— 它们占掉窗口，v2 的 head 就吃掉 111/256
2. **陈述按重要性排序** —— 只有前 1~3 条进向量。实测：
   - "每轮摘要变成几倍"：B 0.906 / A 0.886（B 里 13 倍那条排在第 3）
   - "注入通道有几个"：A 0.907 / B 0.870（A 的第 1 条就是通道清单）
   差 0.02~0.04，正好等于有效信号量级
3. **单条陈述别太长** —— v2 第 1 条 132 token，一个人吃光整个窗口

→ 建议：陈述按 `rejected > decision > constraint > fact > procedure` 排序，单条 ≤ 60 token。

## 13. pi-mem 的对照（npm:pi-mem 0.1.0，github/georgebashi/pi-mem）

| 维度 | pi-mem | 我们 |
|---|---|---|
| 摘要位置 | **后台**：`spawn("pi", ["--mode","json","-p","--no-session","--no-tools"])` 起无头子代理 | 后台 detached `mem.py segment finalize` |
| 摘要模型 | 独立配置 `summaryModel`（默认 claude-haiku-3） | 主端点（现由 `_llm_chat` 调） |
| 触发 | **每次 `agent_end`**（checkpoint 模型） | 段闭合 / 会话结束 |
| 粒度 | **每会话一份，覆盖式**：写完删旧摘要 `deleteSessionSummaries` | 每段一份，累积 |
| 形状 | 固定 7 段叙事（Request / Investigated / Learned / Completed / NextSteps / Files / Concepts） | 不固定条数的 statements[] |
| 向量 | 只对 summary 的 narrative 和手动保存建；observations 不建 | 段向量 = title+digest+陈述前 256 token；陈述提升后各自建 |
| 存储 | LanceDB（向量 + 全文） | SQLite（向量 + BM25 关键词分量） |
| 注入 | 只在 session start，10 条 / 2000 token 预算 | system stable 8 条 + tail 动态 3 条 + 段指针 |

**关键差别**：pi-mem 没有 statements 概念，用"固定字段的叙事"回避了"陈述进不了向量"的问题；
但它也因此无法把单条决策提升成独立可检索记忆。

**可借鉴**：一会话一份覆盖式摘要（避免段数爆炸），但保留 per-turn 段的指针（原文可达）。

## 14. 陈述质量与"跨段推翻"

### 14.1 现状盘点

| 能力 | 有没有 | 位置 |
|---|---|---|
| 短句/省略句还原（"可以""赞同"） | **规则有**，在 `SEGMENT_PROMPT` | 提示词第 2 段 |
| 输出形式约束（主体+动作+对象+数值） | **没有**，只有"自足/无歧义"这类形容词 | — |
| 输出自检（代词残留、主体缺失） | **没有** | — |
| 写记忆时冲突检测 | 有（同域 top-1，`looks_contradictory` + `numeric_conflict` → `disputed`） | `cmd_add` |
| 推翻操作 | 有 CLI `supersede`，但**没暴露成工具** | `cmd_supersede` |
| 图上的矛盾边 | 有（几何 ≥0.94 + 词面 → `contradicts`） | 建图 |
| 段级跨段矛盾检测 | **没有**（L2 只看单个段） | — |

### 14.2 实测：省略句还原的实际效果（seg-2e1f62，22 条陈述）

- 含指代/省略词的陈述：4 条，逐条看**都是误报**（"该 session"的前置就在同句里）
- 明确写出"用户选择/要求"的陈述：**1 条**（drain 的 mtime 判定）
- 用户原话里的 "1.支持后者" → 被还原成
  "drain 扫描 stale 段的条件采用：mtime 早于 now-300s …（用户选择按文件最后修改时间判断而非固定 120 秒）"
  —— **这个是对的**，指代被替换成了具体条件
- 用户原话 "3.段落索引可以的, 不是太大我都支持" → 变成
  "段索引块建议放 5 段、digest 截 40 字…" —— **表态主体丢了**，读起来像助手的建议而不是用户的决定

结论：**规则继承了，但只在"句子够长"时生效；纯表态句会退化成中性条目。**

### 14.3 建议的提示词补丁

```
每条陈述必须能回答五件事：谁 / 对什么 / 做了什么 / 在哪个范围 / 有什么数值约束。
主语是用户时，必须写"用户<表态动词>了<具体决策>，并要求<可执行动作>"。

反例：用户表示赞同。
正例：在 pi 适配器的段容量估算中，用户支持把 CHARS_PER_TOKEN 从 3 调整为 1.73，
      并要求同步修正 SEG_MAX_TOKENS，避免段实际容量被低估 1.7 倍。
```

再加一个**输出自检**字段（一次调用内完成，不加成本）：

```
selfcheck: {"has_pronoun": false, "subject_explicit": true}
```
`has_pronoun=true` 或 `subject_explicit=false` → 打回重写一次，仍不合格则不提升为 decision。

### 14.4 跨段矛盾：前台 vs 后台的真实边界

用户的判断需要修正一半：

- **后台也能做**：L2 本来就是一次 LLM 调用，只要在提示词里附带"同域 top-3 相关旧记忆"，
  它就能判断"这条是否推翻了已有条目"，并输出 `supersedes: ["mem-..."]`。
  成本约 +150 token / 段，可忽略。
- **前台独有的**：主模型同时握着"当前意图"和"被注入的旧记忆"，
  能识别"用户这次的说法与三个月前那次决定不兼容"这类需要理解语境的矛盾。后台只看到两个文本片段。

所以两条都要：

```
后台（常态）：L2 附带同域 top-3 旧记忆 → 输出 supersedes → 直接落 disputed/superseded
前台（兜底）：暴露 mem_supersede / mem_add 工具，主模型发现矛盾时能动手，而不是只能在正文里说
```

现在的缺口：`mem_supersede` 只有 CLI，**没有注册成工具**（只注册了 `mem_search`、`mem_fetch`），
所以前台即使发现矛盾也无法写回。

### 14.5 一条硬约束（影响收口粒度）

实现"赞同类还原"要求段原文里**必须包含被赞同的那个提议**。
- 现状（15 轮一段）：提议在段内，能还原
- **每轮收口：段内只有用户消息 + 本轮回答，上一轮提议在窗口外 → "赞同"无法还原**

→ 若改成每轮收口，切片必须**往前多带一轮**（上一轮的助手回答），否则 14.2 那个正确案例会退化成"用户表示赞同"。

## 15. 决策（2026-11-10）：只做前台，不再维持双路

**理由**：前后台并用要协调两套逻辑（谁能推翻谁、谁先写、冲突谁负责），维护成本超过收益。
用户明确选择：**只用前台**。

### 15.1 分工

```
每轮结束（主模型）  mem_turn_close
  ├─ 本地收口（写 mem_segments，0 token 的 LLM 成本）
  ├─ 摘要（title/digest/statements，本地磁盘，不进正文）
  ├─ 提升 decision/rejected → mem_items
  └─ 逻辑比对：返回可能冲突的旧条目，模型确认后调 mem_supersede

关窗（后台，但不调 LLM）
  └─ segment finalize --no-enrich：只收口，防止断电丢段

不再使用
  ├─ detached L2（`segment finalize` 的 enrich 部分默认关闭）
  └─ harvest 子进程（MEM_FOREGROUND_ONLY=0 可临时回滚）
```

### 15.2 新增接口

| 接口 | 参数 | 行为 |
|---|---|---|
| `mem_turn_close`（工具） | title ≤20 / digest ≤120 / statements ≤12 / supersedes[] | 调 `segment commit`：收口 + 摘要 + 提升 + 返回冲突候选 |
| `mem_supersede`（工具） | old_id / text / claim_type | 调 `supersede --new-text`：写新条（origin=user, verified=1）→ 旧条 superseded + replaces 边 |
| `segment commit`（CLI） | --session --scope --turn --last-entry-id --transcript --payload @file | 一次完成上述链路；自检不通过返回 errors，不写库 |
| `supersede --new-text`（CLI） | old + 新文本 | 不需要事先拿到新条 id |
| `segment finalize --no-enrich` | — | 只收口，不调 LLM |

### 15.3 陈述自检（本地正则，零 LLM）

```
title ≤ 20 字、digest ≤ 120 字
statements ≤ 12 条，每条 8~200 字
禁止指代词：这个/那个/它/该方案/此方案/上述/前者/后者/这样做/这种方式
kind ∈ {decision, preference, constraint} 时必须有明确主体（用户/系统/pi/模型…）
不合格 → 返回 errors，模型改写后重试；不写库
```

### 15.4 顺带修掉的两个 bug

1. **dedup 把数值矛盾当成重复**：`cmd_add` 的去重只查 `looks_contradictory`（否定词），
   不查 `numeric_conflict`。所以"把 3 改成 1.73"会被判为旧条重复合并，新决定直接消失。
   已修：数值不同 → 不走 dedup。
2. **supersede 写入的新条是 draft**：origin=self + 无端点 → `decide_status_and_verified` 降级为 draft，
   检索不到。已改为 origin=user + evidence → active, verified=1。

### 15.5 代价与已知限制

| 项 | 数值 |
|---|---|
| 每轮输出 token | 约 1.2K（12 条陈述实测 1,246），miss 等价 ≈ 3.7K |
| 每轮额外往返 | +1 次工具调用（当前每用户轮已 16.4 次） |
| 晚一轮 | 工具调用时本轮回复可能还没落盘，`segment get --part` 可能缺最后几段话（不影响 L2 结果） |
| 忘了调用 | 尾部提示只在**漏记时**出现一次；仍漏则只有 L1 标题 |

**核心收益**：上下文完整，`赞同/可以` 类省略句能还原（后台切片再修也缺跨段语境）；
推翻操作在同一轮内完成，不依赖队列。

## 17. 统一入口的落地形态（2026-11-10 决定）

### 17.1 三条约束先分清

| 维度 | 是否统一 | 理由 |
|---|---|---|
| **入口** | ✅ 统一 | 只有一个每轮钩子，宿主只认一个契约 |
| **进程** | ✅ 统一 | 4 个 py 各自启动 = 4 × 0.9s；合成 1 个进程 |
| **表结构** | ❌ 不统一 | 强制同表已被证明成本极高；KB 用 LanceDB，专注用 goals 表，各过各的 |

一句话：**四个库共用入口，不共用表；四个文件，一个进程。**

### 17.2 目录形态

```
pi-package/
  hook.py            ← 唯一入口（宿主只调它，或由 memskill 顺序调用四个 lane 函数）
  mem.py             ← 持久记忆 + 工作记忆（已共享 mem.db，拆开成本 > 收益）
  kb_lane.py         ← 薄适配：转调 源码-知识库/v0.1/search_v2.py（LanceDB，默认关）
  focus_lane.py      ← 新增：goals / progress（独立表或独立 db）
```

暂不拆 mem.py：`mem_items` 与 `mem_segments` 共用同一套 embedding、graph、打分，
拆成两个文件要复制 1500 行，违反"降低维护成本"的初衷。
**等 focus/kb 稳定后再考虑**，且只拆"存储"，不拆"检索内核"。

### 17.3 统一返回契约

```json
{
  "v": 1,
  "system": "永不变化的部分：stable 8 条 + 目标清单",
  "tail":   "每轮变化的部分：[mem:now] / 段指针 / 进度 / [mem:kb]",
  "lanes":  { "persistent": "ok|empty|timeout", "working": "...", "kb": "off", "focus": "..." },
  "debug":  { "ms": { "persistent": 12, "working": 3, "focus": 1 } }
}
```

失败隔离：每个 lane 独立 try/catch + 超时，挂了只降级该 lane，绝不让整轮注入失败。

### 17.4 四条通道的门槛（沿用代码已有数值，不重新标定）

| 通道 | 门槛 | 位置 | 预算 |
|---|---|---|---|
| 持久记忆 | `ABS_FLOOR 0.18` 且 ≥ `0.75 × best`；`STABLE_K 8`；单条 180 字；decay×trust；verified≥1 优先 | system(stable) + tail(3) | 300ms |
| 工作记忆 | 无门槛（当前会话必带）：当前段指针 + 最近 1 段 | tail | 50ms |
| 知识库 | 更高（待标定，先设 0.55 且只带 2 条摘要） | tail | 800ms，默认关 |
| 上下文专注 | 目标 active 必带；进度仅检查点 | system(目标) + tail(进度) | 10ms |

持久记忆的既有阈值（代码里已有，不要再新造一套）：

## 19. 工作记忆 vs 持久记忆 —— 不许混淆（2026-11-10）

### 19.1 三者的边界

| | 持久记忆 | 工作记忆 | 注意力（focus） |
|---|---|---|---|
| 存哪 | `mem.db`: `mem_items` | `mem.db`: `mem_segments` + `mem_segment_state` | `focus.db`: `goals`（独立库） |
| 生命周期 | 跨会话，靠衰减老化 | 本会话，随段闭合归档 | 目标关闭即失效 |
| 写入 | `add` / 陈述提升 / `supersede` | `mem_turn_close` 每轮 | 暂不接入 |
| 入选门槛 | **高**：sim≥0.18 且 ≥0.75×best，verified≥1 优先 | **无**：当前会话必带 | 只带 active |
| 可被推翻 | 可以（supersede + replaces 边） | 不适用（原文指针，不改写历史） | 可以（状态改 done/dropped） |
| 用途 | 经验/决策/事实/偏好 | 被压缩历史的撤销键 | 当前在追什么 |

### 19.2 三条不许越界的规则

1. **工作记忆不写 `mem_items`**。段的价值是"指针 + 摘要"，不是"结论"。结论要进持久记忆，必须走陈述提升或显式 `add`，且过门槛。
2. **持久记忆不存原文**。原文留在会话 JSONL，用 `mem_segments.first_id/last_id` 指过去；把原文塞进 `mem_items` 会撑爆检索面。
3. **注意力不放事实**。`goals.goal` 只能是一句目标；"为什么这么定"属于持久记忆的 decision。

### 19.3 共用入口，不共表

```
hook（读，串行三任务）
  A persistent + working  ← 同一次 retrieve，共用嵌入器
  B kb（默认 off）
  C focus（默认 off，注意力，独立 focus.db）
```

串行是为了避免并发 debug；`lanes` 字段报告每路状态，任一路失败只降级自己。

### 19.4 本轮已定

- focus 表 5 字段：`id / scope / goal / status / updated_at`，独立 `focus.db`，文件头注明「注意力」
- hook 三任务**串行**，不并行
- 向量入参收紧（`_seg_vec_for_index`）：**存储保留 title 40 / digest 200，进向量时取 title 20 / digest 100 + 陈述**

### 19.5 向量窗口实测（为什么收紧）

| 方案 | title+digest | 占头部 | 留给陈述 |
|---|---|---|---|
| 存储态 40/200 | 240 字 | **194 token** | **62** |
| 入向量 20/100 | 120 字 | **103 token** | **153** |

没有陈述时**不收紧**——此时 title+digest 就是全部信息。

## 21. 段检索基准 segbench（2026-11-10）

### 21.1 为什么

记忆条目有 `eval_mem.py`，段（工作记忆）一直没尺子。没有尺子，切段阈值、摘要长度、向量窗口、
域激活权重只能靠感觉调。`eval_seg.py` 补上。

### 21.2 出题方式（关键：query 与段独立产生）

不复用摘要倒推自己，而是：

1. 取有原文的段（`mem_segments.transcript` 指向会话 JSONL）
2. 按段的 `turn_start..turn_end` 从原文里取**用户当时的原话**
3. 答案为该段 id
4. 过滤寒暄/纯确认/注入块；`--snapshot` 冻结成 `segbench.json`，跨版本可比

当前冻结集：**23 条用例**（21 段有原文，每段最多 2 题）。

### 21.3 结果

| 版本 | Hit@1 | Hit@3 | Hit@5 | MRR |
|---|---|---|---|---|
| 基线（覆盖只用 title+digest，0.65/0.35） | 43.5% | 65.2% | 73.9% | 0.563 |
| **陈述参与覆盖** | 52.2% | 78.3% | 87.0% | 0.650 |
| **+ 权重 0.50/0.50（现默认）** | **60.9%** | **87.0%** | **87.0%** | **0.717** |

延迟中位 14 ms。

### 21.4 结论

1. **陈述比标题摘要更贴近提问**：只把 `statements` 拼进覆盖文本，Hit@1 +8.7 点、Hit@3 +13.1 点，
   逐条比对 5 条变好 / 1 条变差，不是噪声。
2. 权重 0.65/0.35 → 0.50/0.50 再 +8.7 点，但**样本只有 23 题**（差 2 题），

   门槛的意义是防噪声，不是防漏，暂不动；但要知道"首轮域激活不是必中"。

| 20/100 + 陈述 200 | 170 | 0/35 | 52.2% | 87.0% | 0.667 |
| 陈述 200 放前面 | 170 | 0/35 | 56.5% | 78.3% | 0.677 |
| 只留陈述 200（丢掉头） | 122 | 0/35 | 47.8% | 78.3% | 0.612 |

配对比较（逐题看名次升降，比总分可靠）：

| 变体 | 变好 | 变坏 |
|---|---|---|
| 陈述 300 | 0 | 1 |
| 陈述 120 | 1 | 2 |
| 陈述 200 | 1 | 3 |
| 40/200 不收紧 | 1 | 1 |

**结论：窗口不改，维持 title 20 / digest 100 / 陈述不设上限。** 三条理由：

1. 所有变体都在噪声内（23 题下 1 题 = 4.3 点，最多翻转 3 题）；
2. 唯一稳定的信号是**丢掉头部最伤**（只留陈述 200 → Hit@1 47.8%，掉 13 点）——
   说明"头 + 其后长陈述"这个组合是对的；
3. 段陈述均长 501 字（最长 3104），19/35 段确实超 256 token 被截断，
   但**显式砍陈述反而变差**：e5 截断保留的是"头 + 陈述前若干字"，
   现网等于自动做了这件事，再手动砍只会把有用的陈述尾部信息提前砍掉。

**顺带发现（尺子的局限）**：`--frozen` 冻结的是题目，不冻结候选池。
池从 32 段长到 35 段后，同一份代码现算从 60.9/87.0/0.717 漂到 60.9/82.6/0.714
（min-max 归一化跨池计算，1 题翻转）。跨版本比较必须同池同跑，不同时间点的
独跑分数只能当参考，不能当回归判据。

## 4b-2 域激活门槛与槽位标定（2026-11-10 17:0x）

同一把尺子（23 题冻结集，池 35 段，权重 0.50/0.50）。门槛不改排序，只改
「返回几条 / 一条都不返回」，所以看生产口径 Hit@k、空返回率、平均返回条数。

**首选分分布：最小 0.690，中位 0.968，最大 1.000。**

| 门槛 | Hit@1 | Hit@3 | MRR | 空返回 | 均返回 |
|---|---|---|---|---|---|
| 0.00（纯 k=3） | 60.9% | 82.6% | 0.696 | 0/23 | 3.0 |
| 0.30 / 0.35 / 0.40 / 0.45 | 60.9% | 78.3% | 0.681 | 0/23 | 2.7→2.3 |
| **0.50（现网）** | **60.9%** | **73.9%** | **0.667** | 0/23 | 2.3 |
| 0.55 / 0.60 | 60.9% | 73.9% | 0.667 | 0/23 | 2.1 |
| 0.65 | 60.9% | 69.6% | 0.645 | 0/23 | 2.0 |
| 0.70 | 60.9% | 65.2% | 0.630 | 1/23 | 1.7 |

槽位（门槛固定 0.50）：

| k | Hit@1 | Hit@2 | Hit@3 | Hit@4 | Hit@5 | 均返回 |
|---|---|---|---|---|---|---|
| 3（现网） | 60.9% | 69.6% | 73.9% | — | — | 2.1 |
| 5 | 60.9% | 69.6% | 73.9% | 73.9% | 78.3% | 3.4 |

**正确答案名次分布（前十内）：1 名 14 题、2 名 2 题、3 名 3 题、5 名 1 题、前十外 3 题。**

### 结论：门槛 0.50、k=3 都不动

1. **门槛从不砍首选**（首选分最小 0.690 > 0.50），只砍第 2/3 条弱候选——正是设计意图
   （"别拿弱候选填满槽位"）。
2. 降到 0.30-0.45 能多回收 2 题（82.6% vs 73.9%），但被回收的是 rank-3 且分 0.459 / 0.299 的
   两条，本身属于弱候选；**且这把尺子每题只标 1 个正确答案，量不出 precision**，
   为了 +2 题放松闸门等于用噪声换噪声。
3. k=3→4 零收益，→5 只多 1 题（4.3 点，噪声内）却多吃 1.4 条。不划算。
4. **真正该修的是尺子**：需要能标"多条返回里有几条算相关"（例如同会话相邻段记 0.5 分），
   否则门槛永远只能靠猜。

### 附带发现

- **3/23 题（13%）完全检索不到**，逐条看：一条答案段的标题是 L1 兜底（原始用户文本片段，
  不是摘要），两条是跨 4+ 轮的长段（一个段里塞了多个话题，向量被平均掉）。
  指向的是**摘要/切段质量**，不是打分公式——这正是「4b 不可测组」缺的线索。
- **`turn_start/turn_end` 倒挂污染统计**：`seg-db69d8` 是 `23→2`。跨度分组因此把它算进
  "1 轮"，`brief --min-turns` 也踩过同一个坑（已在显示层兜底，数据层未修）。
  按跨度分组看 Hit@3 因此不可信：1 轮 71.4%（5/7）、2-3 轮 92.3%（12/13）、4+ 轮 2/3，
  样本太小且被倒挂段污染，只能当弱信号。

## 4b-3 摘要质量标定（2026-11-10 17:2x）——本次唯一显著收益

前三组的结论都是"别动"，这组不一样。怀疑点来自 4b-2：3 道完全搜不到的题里，
答案段的标题是 **L1 兜底标题**（原始用户文本截断，不是摘要）。

做法：对 11 条 `enriched=0` 的段用生产 LLM（`_seg_enrich_one(dry=True)`）离线补摘要，
**同一进程内**先量现网、再落库、再量，池固定 38 段，只有 6 段的 title/digest/vector 变了。

| 变体 | Hit@1 | Hit@3 | Hit@5 | MRR |
|---|---|---|---|---|
| A 现网（L1 兜底标题） | 60.9% | 82.6% | 87.0% | 0.704 |
| B 只换摘要、不加陈述 | 56.5% | 87.0% | 87.0% | 0.703 |
| C 生产写法（摘要 + 陈述） | 65.2% | 87.0% | 91.3% | 0.755 |
| **D 真落库后（实测）** | **60.9%** | **87.0%** | **91.3%** | **0.750** |

（B 的 Hit@1 掉、Hit@3 涨，说明**摘要负责"进前十"，陈述负责"排第一"**：两者分工不能只留一个。）

逐题变化（A→D）：

```
#02  99 → 1   侧会话有简略模式吗? 只保留问答, 不全量拉取代码思考
#01   1 → 2   > "甚至你不必在代码设置上限, 只需要保证工具被反复调用不会出错即可"
#03/#04/#16  各升 1 名
```

D 与 C 的差别来自 LLM 摘要的不确定性（同段两次生成标题不同），差 1 题，属噪声。

**结论：L1 兜底标题确实拖后腿，已用生产路径补齐 6 段（enrich + 提升 20 条陈述）。**
剩下 5 段补不了：`transcript` 为空（旧 bug 遗留），`_seg_source_text` 拿不到原文 →
`source_too_short` 直接跳过。要么回填 transcript，要么永久保留 L1 标题。

**副产品：摘要质量是"4b 不可测组"的第一把可量尺子。**
"切多少轮一段"确实量不出来，但"同一批段换更好的摘要能涨多少"量出来了（+4.4 点 Hit@3、+0.046 MRR）。
说明后续要提检索命中，优先做摘要质量而不是调公式。

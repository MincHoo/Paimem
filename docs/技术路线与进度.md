## 三、技术路线

```
                    ┌─ finewiki zh ─┐
语料源 ──────────────┼─ finewiki en ─┼─→ 切块 ─→ 嵌入(e5-small fp16 GPU) ─→ LanceDB ─→ 混合检索
                    └─ github-code ─┘      │                                  │
                                            │                        向量 ∥ BM25(RRF)
                                       质量过滤 + 去重                        │
                                                                      按 page_id 聚合回填
```

### 索引结构（父子两表 + L0）

| 层 | 表 | 字段 | 说明 |
|---|---|---|---|
| L0 | `pages` | page_id, title, url, wikidata_id, first_para, sections | 条目主键、别名、展示兜底 |
| P | `parents` | parent_id, page_id, section_path, n_children, full_text | **完整文本只存这一次** |
| C | `children` | chunk_id, parent_id, seq, start_idx, end_idx, vector | 只存偏移，**不存文本** |

存储账：父表文本量 = 原文量（父文本就是子块拼起来）；子表每块多付 16 B 偏移。
总量与单表方案持平（英文 8M chunk ≈ 20 GB），因此 **raw 可以放心删**。

### 检索策略（铁律）

```
query → BM25(标题/正文) ∥ 向量(child 级) → RRF 融合
      → 取 top-20 child
      → 按 parent_id 去重
      → 取 top-3~5 父级
      → 父级 ≤4 块：返回整父小节
        父级 >4 块：返回 命中块 ±1 块（seq 窗口）
```

1. **必须按 parent_id 去重**：否则同一父级被展开多次，10 子块会膨胀成 10,000+ token（5 倍浪费）
2. **返回粒度 = 小节，不是全文**：全文 3–20 KB，其中 80% 与问题无关，噪声稀释
3. **去重必须在父级做**：若子块去重删掉一个，父文本会出现空缺，偏移错位

代价：去重后父级数可能少于 k，命中多样性下降——父子结构的固有取舍。

### ⚠️ 统一 Schema（重点：不统一就要写两套筛选代码）

**目标：wiki 与 code 的表结构完全同构，检索层只写一套逻辑，用 `source` 分流。**

### 不统一会怎么样

- `where lang='zh'` 会误伤代码语料（它用 `language='Python'`）
- 排序/去重/截断/回填要写两套分支
- 混合检索（RRF）的元数据归一化又要写一遍

### 现状缺口（6 处）

| # | 问题 | wiki | code | 修法 |
|---|---|---|---|---|
| 1 | **代码缺父级** | 小节 | **无** | parent = 整个文件（imports+类+同级函数都在文件里） |
| 2 | **语言字段语义冲突** | `lang='zh'` | `language='Python'` | 拆为 `lang`(自然语言) + `plang`(编程语言) |
| 3 | **代码无溯源链接** | 有 `url` | 无 | `https://github.com/{repo}/blob/HEAD/{path}` |
| 4 | **两边都无 seq/偏移** | 无 | 无 | 加 `seq / start_idx / end_idx` |
| 5 | **维基缺 license** | 无 | 有 | 父表写 `CC-BY-SA-4.0` |
| 6 | **去重层级不一致** | chunk 级（会挖空父文本） | 文件级+chunk 级 | **两边统一到父级去重** |

### 统一后的表结构

```python

parent_id, doc_id, source, title, full_text, n_children,

# children（两语料同名同结构）
chunk_id, parent_id, doc_id, seq, start_idx, end_idx,

```

### 字段映射

| 字段 | wiki 填什么 | code 填什么 |

### 代码侧的额外要求：取回必须「通用」

| 情况 | 返回策略 |
|---|---|
| 符号 ≤1500 字符（绝大多数） | 直接返回整个符号，天然可读 |
| 符号 >1500 字符 | 返回命中段 ± 相邻段（seq 窗口），可重拼 |
| 类 ≥1500 字符 | 返回命中方法 ± 相邻方法 + 类签名 |

上下文头保留：`// path` / `// symbol` / `// class` / `// imports`（代码版的「标题 > 小节」）。
另建议加 `signature` 字段，命中后先展示签名，再决定是否展开全文。

**`content_hash` 不入 LanceDB**（只在中间 parquet 保留），12M chunk 能省 480 MB。

#### 6. 记忆库 5 条 CHECK 约束（已修正）

```sql
CHECK (verified = 2 → evidence_ref IS NOT NULL)                  -- 工具实证必须有锚点
CHECK (verified > 0 → origin IN ('user','tool','self'))          -- 允许 self，但必须有锚点
CHECK (revoked_at IS NULL → 参与在线召回)                         -- 撤销即退出召回
CHECK (cold = 1 → hot_score < COLD_THRESHOLD)                    -- 状态与分数不打架
CHECK (origin = 'self' AND evidence_ref IS NULL → verified = 0)  -- ★ 修正项
```

**第五条为什么改**：原写法 `origin='self' → verified<=0` 过严，会把「模型用工具实测得到的结论」永远挡在 L1 外，只能当断言——而这恰恰是最硬的知识。
正确语义：**没有外部锚点的 self 条目不得自称已验证**；带真实 `tool_call_id` 的允许升到 `verified=2`。

#### 6.5 模型注册表与档位判定

```sql
model_registry(
  model_id        TEXT PK,     -- 'bonsai-9b-q4' / 'glm-4.6' / 'claude-sonnet-4.5'
  tier            TEXT,        -- large | medium | small
  deploy          TEXT,        -- local | remote
  params_b        REAL,
  active_params_b REAL,        -- MoE 按激活参数算
  quant           TEXT,        -- fp16 | fp8 | q8 | q4
  ctx_window      INT,
  tool_call       BOOL,
  tier_source     TEXT         -- declared | probed
)
```

**两个维度拆开**：「大中小」与「本地」正交，合成一个字段会打架（本地 70B 算哪档？）。

| 档位 | 稠密参数 | MoE 激活参数 | 写入权限 | 注入预算 |
|---|---|---|---|---|
| large | ≥70B | ≥30B | 可写 verified≤1 | 1300 tok |
| medium | 20–70B | 10–30B | 只能写 verified=0 | 1000 tok |
| small | <20B | <10B | 只能写 verified=0 | 800 tok |
| small + local | — | — | **默认不进 L1** | 600 tok |

**校准因子**：q4 量化降一档；ctx < 32k 直接锁 small；无工具调用能力 → `write_authority=0`。

**关键纪律：不让模型自报档位。** 由调用方（harness）在写入时注入 `origin_model`，再从注册表查 `tier / write_authority / inject_cap`。档位是**环境的属性**，不是模型的自我认知。

**档位用 probe 校准，不用参数量猜**：给候选模型 20 条「从工具输出蒸馏 fact」任务，测三项：

| 指标 | 及格线 | 影响 |
|---|---|---|
| 幻觉率（无 evidence 的 fact 占比） | large ≤5% / medium ≤15% / small ≤30% | 决定能否写 L1 |
| 分栏准确率（断言 vs 实证） | ≥85% | 决定能否 `verified≥1` |
| 锚点诚实度（是否自编 tool_call_id） | 零容忍 | **编造一次即永久锁 `verified=0`** |

### 关键决策（已对齐）

| 项 | 决定 | 理由 |
|---|---|---|
| A. 英文范围 | **全量 15 片 + 只索引 ≥2000 字符的条目** | 全量索引会产 2800 万 chunk / 17 小时 / 55 GB，不可行 |
| B. 向量精度 | **fp16**（384 维，768 B/条） | 误差 0.05% 等于无损，索引减半；fp8 无 pyarrow 类型，用不了 |
| C. text 存储 | **父表存全文，子表只存偏移** | 总量不变，且 raw 可删（原「存库」方案已升级） |
| D. reranker | **开关，默认关** | 没有评测集前加组件是玄学，等第 6 步 |
| E. 执行顺序 | 代码 → 中文 → 英文，每步完删 raw | 控制磁盘峰值 |
| F. 后台策略 | 前台受控执行，步骤间对齐 | nohup 后台在 Windows 会留僵尸进程（已踩过，重启才清） |
| G. 返回粒度 | **小节级**（≤4 块返回整节，>4 块返回 seq 窗口） | 全文噪声稀释，子块太碎缺上下文 |
| H. 父级粒度 | **小节**，不是整篇文章 | 整篇 3–20 KB、长尾 100 KB+，单条返回过大 |

### 切块策略

| 语料 | 边界 | 目标块大小 | 前缀 |
|---|---|---|---|
| 维基 | 词条=文档边界，`##` 小节=切块边界 | ≤400 字符(中) / 900(英)，≈200 token | `标题 > 小节路径` |
| 代码 | AST 符号（function/class/method） | ≤1500 字符 | `// path` / `// symbol` / `// class` / `// imports` |

**为什么不用长上下文模型（bge-m3）**：实测块平均只有 **200 token**，远未触及 512 上限，p99 才 514–572。换 bge-m3 只会让速度 ÷5、索引 ×2.7，解决一个不存在的问题。

### 资源画像：切块 vs 建库

| 资源 | 切块 (`chunk_*_v2.py`) | 建库 (`build_index.py`) |
|---|---|---|
| CPU | **单核跑满**（tree-sitter / 正则） | 多核轻度（Rust tokenizer） |
| GPU | 不用 | **吃满**（fp16，VRAM 约 1 GB） |
| 内存 | 中（去重哈希集合会持续增长） | 低（单批数据） |
| 磁盘 | 读 raw，写 chunk parquet（约 1/10） | 写 LanceDB（≈2 KB/chunk）+ 索引临时 |
| 耗时 | 代码 23 min / 中文 5 min / 英文 35 min | 代码 1 h / 中文 2.4 h / 英文 4 h |
| 瓶颈 | 纯 CPU 单线程 | **GPU 算力** |

**关键**：两者资源正交——切块不用 GPU，建库不占满 CPU，**可以流水线并行**（切下一份的同时建当前份的库）。理论上总时长可从 7.7 h 压到 ≈ GPU 纯耗时 7.4 h，切块时间完全隐藏。
但代价是内存与磁盘 I/O 竞争，且需两路日志监控；第一版建议**串行跑**，先求稳。
